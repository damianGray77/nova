# Results: the settings registry

Step 1 of `docs/config-plan.md` (call C1, and C5's `nova keys`), approved by Damian as recommended. Built 2026-11-07.

## What was built

- **The registry.** `core/src/keys.inc` is the table: one entry per setting, with its name, kind (switch, whole number, number, choice or text), default, minimum and maximum, a choice's options, its group (config-plan C2's draft list), a short label, one line of help (drawn from `docs/design.md` and the code's comments), and flags: logarithmic knob, hidden (tests and demos), computed default, computed maximum, and "above the minimum" (an open lower bound). Each entry also names the switch it depends on (`needs`). `core/src/keys.cpp` expands it once, on first use, and holds the readers, the checks, and the two printers. `core/include/nova/keys.h` documents the whole API at its top: how to add a setting and how to read it.
- **Families** are written once, as templates with a `<set>` placeholder, and expanded for each member of the set:
  - `<spread>.spread|smooth|barren|hotspots|hotspot_boost|against`, for `spark` and `res.memory|cpu|gpu|npu|disk|ecpu` (the spark member lands in the Sparks group, the rest in Resources);
  - `heat.<unit>.warm|hot|max|speed_min|err_max`, for `cpu`, `mem`, `gpu` and `npu`, with `heat.mem.hot`'s own default of 70 (`NOVA_DEFAULT`);
  - `vary.<vres>` (`soup_size`, `millicores`, `gpus`, `npus`, `spark_rate`, `disk`: procedural worlds only) and `vary.<vprop>` (`cool`, `radiation`, `volatility`, `endurance`, `noise`: procedural and landscape);
  - `budget.<budget>_was`, for `memory`, `disk`, `gpu` and `npu` (hidden: the record of a resolved budget).
- **Every read goes through its entry.** All of the engine's reads (about 250 call sites) in `soup.cpp`, `world.cpp`, `budget.cpp`, `lineage.cpp` and `app/main.cpp` now name the key and take its default and range from the registry. The old local helpers (`get_u32`, `get_f64`, `get_u32_in`, `get_f64_in`), the hand-written range checks in `lineage.cpp` and `read_run_keys`, and the choices' hand-written "must be a or b" checks are gone. The live knobs' range checks (`World::parse_knob`) use the registry too. Outside `keys.cpp`, no code in `core/` or `app/` calls Config's raw getters any more, and the keys suite keeps it that way. (`run.cpp`, `cost.cpp` and `landscape.cpp` turned out to read nothing themselves.)
- **The seeding pass.** A temporary recording mode in `Config` (and in the two files' range helpers) logged every read, with its reader, the call site's default and its range check, while all 38 suites ran and a stub of the keys suite loaded every preset with real defaults. That gave 377 distinct (key, reader, default, range) lines for 246 keys. 11 lines were tests reading the effective config back (test code, not the engine) and were dropped. `lineage.cpp`'s hand-written ranges and the app's run keys (the tests don't run the app) were added by hand. The result is kept as `tests/keys_seed.txt` (384 lines), and the keys suite checks the registry against every line. The recording mode was then removed: `config.h` and `config.cpp` are unchanged.
- **`nova keys`** prints the registry as a table, group by group. **`nova keys --md <path>`** writes the Markdown reference. `docs/keys.md` is generated by it, and the keys suite fails if it goes stale. The command is in the usage text and in the README's layout table.
- **The `keys` suite** (`tests/test_keys.cpp`) checks:
  - every entry: a valid, unique name; a known group; a label and one line of help; a default inside its range; a choice's default among its options; `needs` naming a real switch (and real options); flags only where they make sense;
  - the families: 42 spread keys, heat curves with `heat.mem.hot` at 70, the vary split, the four `_was` records;
  - the seeding pass: every recorded read has an entry of the same kind, the same default (unless computed, or one of the budgets' two assumptions below) and the same range (unless the maximum is computed);
  - every preset loads through the registry as a run would (budgets, then the world, real defaults, no test fallback), every key in every preset has an entry, nothing in a preset goes unread, and, with one custom-table world added, every entry is read at least once (no entry is unreachable);
  - the fallback defaults still win over the registry's, computed defaults included, and a config's own value beats both;
  - an unknown key in a config still fails as unused; reading a key with no entry, with the wrong reader, or without (or with an unwanted) computed part is caught; bad values report as before;
  - `nova keys --md` output is well formed (every table row has its header's columns, one section per non-empty group, every setting named) and `docs/keys.md` matches it;
  - no engine source reads a setting around the registry.

## The API, briefly

```cpp
// keys.inc: one entry per setting (help last).
NOVA_WHOLE("disaster.every", 0, 0, 1000000000, 0, "Disasters", "Disaster interval",
           "disaster.enabled", "Ticks between disasters on average (0 = never).")

// The engine: read by name, with the reader for the kind.
const u32 every = key_u32(cfg, "disaster.every");
```

- Macros: `NOVA_FLAG`, `NOVA_WHOLE`, `NOVA_NUMBER`, `NOVA_CHOICE`, `NOVA_TEXT` (name, default, [min, max | options], flags, group, label, needs, help); `NOVA_MEMBER(set, member, label, group)` for families; `NOVA_DEFAULT(name, default)` for one member's own default.
- Flags: `kKeyLog`, `kKeyHidden`, `kKeyComputed`, `kKeyMaxComputed`, `kKeyOpenMin`; `kKeyNoMax` for no upper limit.
- Readers: `key_flag`, `key_u32`, `key_u64`, `key_i64`, `key_f64`, `key_choice` (always returns one of the options), `key_str`, and `key_text` (any kind, as written). Computed parts come from the call site: `key_default(v)`, `key_max(v)`, `key_default_max(v, m)`. Supplying one the entry doesn't declare, or leaving out one it does, is caught.
- Peeks for estimates made before the world reads (the budgets): `key_peek_flag|u64|f64|str`, with no range check.
- Live values: `key_check(name, text, at, &out)` (the knobs).
- Introspection for the page and the docs: `key_count`, `key_at`, `key_find`, `Key` (name, kind, flags, def, lo, hi, def_text, options, group, label, needs, help, family, family_label, family_help), `kKeyGroups`, `keys_table`, `keys_markdown`.
- A bad value goes through `cfg.fail`, so the run refuses to start. A misused read stops the process (`NOVA_FATAL`) with the key and the fix; the keys suite swaps in a hook (`key_set_misuse_hook`) to watch it, and traces reads with `key_set_trace_hook`.

- 11 hidden (the demo world's 7 keys and the 4 budget records).
- 22 with computed parts: 17 computed defaults and 7 computed maxima (`world.pool_initial` and `spark.max_len` have both).

## Settled details and deviations

1. **The budgets keep two assumptions of their own.** `budget.cpp`'s estimates read two settings with defaults that differ from the engine's: `cpu.instr_per_core` 25,000 (the presets' value; the engine's default is 1,000), used by `budget.gpu`/`budget.npu`'s calibration, and `salvage.ratio` 0 (the engine's default has been 4 since Phase 10), used by `budget.disk` and the disk fit check. Switching them to the registry's defaults would change `world.disk` for a `budget.disk` run that leaves `salvage.ratio` unset, and could make a resumed snapshot fail its fit check on a tight disk. So they stay as they were, read with `key_peek_u64_assuming` / `key_peek_f64_assuming`, which `keys.h` marks as not for new code. *For Damian:* the salvage one looks like a stale default. With salvage on, a disk codon takes 9.125 bytes in its file, not 5.125, so on the default rules `budget.disk = 20GB` gives a disk tier of about 36 GB, and the fit check underestimates by the same factor of about 1.8. Fixing it is a one-line change, but it changes those worlds.
2. **`mem.decay`** keeps its old acceptance: anything below 0 (it used to default to -1) still means "work it out". So its range is -1 to 1, and the entry is marked computed, with the call site supplying the worked-out value. The computation (Ray's background rate) moved a few lines up, unchanged.
3. **Choices are checked by the registry,** with the message built from the options: "must be ring, procedural or landscape", the same words as before for every choice. The exception is `<spread>.against`: a word that isn't an option at all now gets "must be none, spark, memory, cpu, gpu, npu, disk or ecpu"; naming the distribution itself still gets the old message. Two run-key messages changed wording: `run.seconds` "must be at least 0" (was "must be 0 (no limit) or more") and `run.after_replicator` "must be -1 or more" (was "... or a tick count").
4. **A bad value gives back the minimum** (a choice, its default), as the soup and world helpers did. `lineage.cpp`'s checks used to give back the default. This only matters once the config is already refused.
5. **Groups** follow C2's draft list: the instruction set (`isa.*`, `tierra.divide_share`) is under CPU and cores; `vary.*` and the vents under Resources; the node lifecycle (`node.*`, `world.land`, `world.drift`, `world.budget`) under World and land; the accelerator mode and devices (`accel.*`) and warps under GPU, with `accel.npu` under NPU; salvage under Contact and eating; `signal.sustained` under Signals; `seed.*` and `world.origins` under Sparks. Substrates and Disasters have no settings yet; the printers skip empty groups.
6. **`needs`** is `"key"` (that switch on, or that number or text non-zero or non-empty) or `"key=a|b"` (that choice is a or b), so the page can grey out settings behind a choice too (`land.*` needs `world.graph=landscape`). Its meaning is only for the page: reads don't look at it.
7. **The table's default for a computed entry** is its value with every other setting at its own default (for example `disk.rot` 1e-8, `hazard.rot` 1.5625e-5). The help says how it is worked out. The real value comes from the call site, as C4's check will show it.
8. **Unknown keys:** reading a key with no entry stops the process, in runs and tests alike, with `nova: fatal: config key 'x' has no entry in the settings registry (add one to core/src/keys.inc)`. A key in a config that nothing reads still fails as unused (`first_unused`), as before.
9. **Config's raw getters stay.** Config is still the generic `key = value` parser, `test_config` tests it, and tests read the effective config back with it. The keys suite guards the engine side: no source in `core/src` or `app` other than `keys.cpp` and `config.cpp` may read a setting with a raw getter.
10. **Not changed:** `World::is_structural`'s prefix list (which decides between "structural setting" and "unknown knob" for a refused live change) could come from the registry too, but that would change some refusals' wording, so it is left for the page work. The 7 live knobs stay live (C3's open question is not part of this step).

## Determinism

No world changes. `verify.ps1` is green: every suite keeps its pinned and gate hashes. Two more checks:

- *Old against new:* an unmodified Debug build of `HEAD` (exported to a scratch folder) and this one:
  - ran all 38 earlier suites with the same output, line for line, apart from the four lines that print a hardware calibration's timing (the budget and device suites);
  - ran `nova run` for 100 ticks on 4 threads, headless on the CPU reference (`accel.gpu`, `accel.npu` and `warp.device` set to `cpu`; the big landscapes cut to 120 nodes of 4,096 codons), on every preset and on a ring, a procedural and a landscape world with nothing but the defaults (24 nodes of 4,096 codons, 40 initial sparks). All 11 printed the same startup lines, events and final hashes (for example `soup` e1f4b1375084d96a, `world` 29d22a4347ddd7e3, `gpu_world` 8dab22457274fd20, the defaults' procedural world 65e67d3818c7d6ae).
- *The seeding pass* checks every recorded default and range against the registry, so a default that drifted would fail the keys suite even where no pinned hash covers it.
